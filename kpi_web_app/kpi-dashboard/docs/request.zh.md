# KPI Web App 重建需求输入规范

## 1. 文档目的

本文档定义了重建 `kpi_web_app` 项目族时，需求方最少需要提前提供的输入包。

涉及的能力域包括：

- Portal 外壳：`kpi-dashboard`
- KPI 异常检测：`kpi-anomaly-detector`
- KPI 报表生成：`kpi-generator`
- 流量编排：`kpi_traffic_model`
- 辅助报表脚本：`get-kpi-report`

## 2. 产品边界必须先明确

在开发前，需求方必须明确：

- 目标是纯 Portal 界面，还是带本地执行能力的平台
- 兄弟仓库是否继续独立存在
- 一期范围包含哪些模块
- Portal 是否负责调度、持久化、审计、恢复

## 3. 必须提供的需求域

### 3.1 业务能力需求

每个能力至少要定义：

- 能力名称
- 业务目标
- 触发条件
- 输入物
- 处理规则
- 输出物
- 失败预期
- 责任团队

### 3.2 功能需求

每个功能至少要定义：

- 功能 ID
- 使用角色
- 前置条件
- 主流程
- 异常流程
- 后置条件
- 验收标准

最小范围应覆盖：

- Portal 首页
- 模块导航
- 上传与校验
- 后台作业创建
- 状态流转
- 详情页展示
- 产物下载
- 重跑、取消、删除
- 环境解析与流量请求提交

### 3.3 数据需求

必须给出：

- 输入文件格式
- 文件命名规则
- 字段校验规则
- 派生字段
- 输出结构
- 保留策略
- 版本规则

关键项目专属契约：

- detector 文件名解析规则
- KPI Excel 输入结构
- generator 请求结构
- traffic model 请求结构
- job 元数据结构
- artifact 元数据结构

### 3.4 集成需求

每个集成点需说明：

- 系统名称
- 集成类型
- 认证方式
- 超时与重试规则
- 失败处理
- 契约版本策略

### 3.5 页面与交互需求

每个页面需说明：

- 页面目标
- 入口路由
- 核心组件
- 校验规则
- 表格列
- 过滤行为
- 空态与报错态
- 自动刷新行为
- 成功提示与下载反馈

### 3.6 编排与流程需求

每个异步流程都要定义：

- 触发源
- 入队规则
- 顺序规则
- 并发规则
- 超时规则
- 取消语义
- 重跑语义
- 重启恢复行为
- 产物归集点

### 3.7 非功能需求

必须给出可量化目标：

- 性能
- 可用性
- 可靠性
- 可扩展性
- 安全性
- 可维护性
- 可部署性
- 可观测性

### 3.8 运维需求

必须定义：

- 环境模型
- 配置来源
- 备份和清理策略
- 产物保留周期
- 回滚策略
- 发布流程

### 3.9 安全需求

必须明确：

- 是否需要登录
- 是否需要 RBAC
- 谁能上传、重跑、取消、删除
- 密钥如何管理
- 是否要求审计

### 3.10 验收需求

验收必须覆盖：

- 功能
- UI
- 集成
- 数据正确性
- 性能
- 部署
- 运维

## 4. 建议需求输入模板

建议在开发前准备以下章节：

- 项目章程
- 模块清单
- 用例矩阵
- 数据契约矩阵
- 集成矩阵
- 页面清单
- 流程矩阵
- 部署与运维矩阵
- 验收清单

## 5. 结论

`kpi_web_app` 不是单纯的网页重建，而是一个 Portal 加能力平台的重建任务，因此需求输入必须同时覆盖 UI 和执行编排。
