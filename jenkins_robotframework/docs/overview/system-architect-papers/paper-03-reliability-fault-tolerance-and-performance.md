# 第三篇：论可靠性、容错与性能设计在 5G 自动化测试平台中的应用

## 适配考点

本文主要适配软件可靠性、容错、并发安全、性能风险控制和可观测性类题目。高可用、负载均衡和完整性能测试只能作为演进方向，不能作为当前已落地实践。

## 论文正文

### 摘要

我参与了某 5G GNB 自动化测试平台的架构设计和核心实现，具体时间、职位和职责须按真实经历确认。平台由 React、FastAPI、Jenkins、Linux Agent、Robot Framework、Python Runner、KPI 工具和 SQLite 组成，任务执行时间长、外部依赖多、测试资源稀缺。原有方式发生代码检出、环境、测试线或回调故障后，往往只能逐段查日志，不安全并发还会争用同一 UE 或 gNB。为此，我从故障预防、隔离、检测、恢复和证据留存五方面设计机制：创建与触发分离，Jenkins 隔离长任务，Runner 实施安全校验和资源锁，回调与产物清单提供可观测性，并以异步化和大文件外置控制性能风险。当前代码与部分服务器基线已形成可追踪、可重试的主链路，完整设备闭环仍待验证。

### 一、项目背景与可靠性需求

任务从浏览器提交后，经 Jenkins 调度 Agent，调用真实测试线，最后回写状态、KPI 和报告。一次运行包含代码拉取、环境准备、设备操作、流量和后处理，任一步都可能失败；UE、应用服务器、gNB、cell 和 RU 又不能被无约束并发操作。我负责运行状态和执行安全设计，确定以下目标：单任务失败不破坏其他记录；触发失败后仍可查询和重试；危险并发在执行前或访问资源时被阻止；成功或失败都尽量保留证据；外部 AI 不可用时仍有基础诊断。可用性和性能结论必须以实测为准，不能虚构“多个九”。

### 二、可靠性、容错和性能设计方法

可靠性是系统在规定条件和时间内完成规定功能的能力，设计内容包括预防、容错、检测、恢复和评估。容错不是吞掉异常，而是限制故障范围并留下可恢复状态。性能则关注响应、吞吐、资源利用和容量。本项目的交互接口与长测试任务属于两类负载：创建和查询应快速返回，Robot/KPI 执行必须异步，不能占用 HTTP 生命周期。

我用质量属性场景验证方案：Jenkins 触发失败时保留运行记录并允许重试；回调暂时失败时保留本地结果；两个任务项命中同一资源时拒绝或串行；大文件生成后列表查询只读元数据；外部 AI 受限时规则分析仍可工作。方案据此同时考虑故障恢复、并发正确性与性能。

在故障分类上，我把问题划分为平台接口、Jenkins 调度、代码检出、Python 环境、Runner、Robot 用例、测试设备、KPI 后处理和回调九类。每类故障分别规定检测证据、状态落点和人工处理入口，避免所有失败只返回一个错误码。可靠性评估则关注任务成功率、失败分层、平均恢复时间、重试结果和产物完整性，而不是只统计服务进程是否在线。

### 三、项目中的具体设计

第一，建立可恢复状态。平台先创建运行记录，再由独立接口触发 Jenkins。平台运行编号与队列号、构建号分离，触发失败不会丢失业务对象，Portal 可对失败状态重试。执行端通过回调更新状态、时间、构建引用和摘要，系统保留已完成事实，不要求用户重新输入全部参数。

状态迁移还设置业务门禁，例如只有已创建或触发失败的运行才允许再次触发，终态结果不被普通操作随意覆盖。当前回调尚需补充幂等键和重放防护，因此论文只把它写成可恢复主线，而不夸大为已经实现“恰好一次”交付。

第二，以 Jenkins 隔离长任务。Web 进程不直接启动 Robot 或 KPI；Jenkins 管理 Agent、阶段日志、超时、凭据和归档。流水线按检出、环境、执行、归档和回调分段，复杂校验下沉到可测试的 Python 脚本。回调脚本具有重试和本地后备文件，但仍需调整归档顺序，才能保证发送结果和失败信息长期保存。

第三，并行与安全同时设计。工作流支持阶段和任务项串并行，但前端选择并行不代表无条件执行。加载阶段先拦截危险组合；运行时按 UE、应用服务器、gNB、cell、RU 和 KPI 后处理域加锁，并按固定顺序获取锁以降低死锁风险；reset、lock 等控制动作默认串行。当前锁是单进程资源锁，不能夸大为跨 Agent 分布式锁。

第四，构建检测与证据链。Runner 结果包含状态、任务时间线、KPI 窗口和产物清单；回调把元数据写入 SQLite；Portal 展示阶段、进度和报告；AI Worker读取控制台、Robot XML、Runner 结果和环境计划，生成失败层及建议。外部 AI 不可用时回退到规则模式，现已覆盖 Robot、代码检出、Agent、Python、UE、超时和 TAF 等典型问题，KPI 与回调故障仍需样本验证。

第五，控制性能风险。接口只负责创建、触发和查询，长任务交给 Jenkins；数据库只存状态、摘要和链接，大文件留在产物目录；仅隔离资源允许并发，并限制工作线程。KPI 时间窗会排除报告生成阶段，但是否准确代表流量窗口仍需真实时序验证。pytest、Postman、数据库校验和 JMeter smoke 分别检查契约、链路、数据和最小性能。

### 四、效果、局限和改进

目前 Agent 连接、Java 和工作目录 smoke，以及平台运行、回调和产物查询契约已有验证记录；Runner 已实现安全校验、资源锁和统一结果。系统可识别触发、检出、环境、Runner、Robot 等典型故障层，并围绕运行编号组织证据。当前单 Jenkins、SQLite 和单实例服务仍是单点，真实 TAF 链路也未完成全部验证，不能宣称生产级高可用。后续将增加回调幂等键和重试队列，完善健康探针、备份恢复和容量基线，再按规模评估 PostgreSQL 与 API 多实例，并用成功率、P95、队列时间和恢复时间持续度量。可靠性设计不是简单堆叠冗余，而是从状态、隔离、检测、恢复和证据全链路控制失败。

## 考场改写提示

- 如果题目限定“可靠性模型或评估”，补充故障率、MTBF、MTTR、可用度和可靠性测试方法，并填入真实数据。
- 如果题目限定“高可用”，应增加冗余、故障转移、数据备份与恢复设计，同时如实说明当前单点和下一阶段方案。
- 如果题目限定“性能测试”，重点展开性能目标、负载模型、基准测试、负载测试、压力测试、稳定性测试、瓶颈定位和回归；JMeter 目前只能写成已有 smoke 资产，不能虚构完整压测结论。
- 如果题目限定“负载均衡”，可从 API 多实例、Nginx 分发和 Jenkins Agent 标签调度提出演进设计，但不要声称当前已部署多实例负载均衡。
- 将任务成功率、P95、MTTR 等指标替换为本人实际测量值。
