# 第二篇：论基于架构的软件开发与架构演化在 5G 测试平台中的应用

## 适配考点

本文主要适配系统建模、基于架构的软件开发方法、构件化开发、架构评估、架构演化和软件维护类题目。

## 论文正文

### 摘要

我参与了某 5G GNB 自动化测试平台的架构设计和核心建设，具体时间、职位和职责须按真实经历确认。项目早期由 Jenkins 调用 Robot Framework，后来需要支持 Web 提交、统一运行记录、Python KPI 工作流、产物聚合和 AI 分析。若只在流水线中增加脚本，将导致边界模糊、接口反复变化。为此，我采用基于架构的软件开发方法，从业务目标和质量属性提取架构需求，以多视图描述系统，通过评估确定 React、FastAPI、Jenkins、Robot/Python Runner、SQLite 和产物存储的职责，再以契约优先方式增量实施。当前代码表明，各模块可围绕统一运行和回调契约独立演进，其余效果仍应以真实项目数据说明。本文论述该方法的设计、评估和演化实践。

### 一、项目背景与问题分析

项目要把“工程师操作 Jenkins”升级为“用户在 Portal 提交、平台统一调度和展示”。系统既要兼容 Robot 用例，又要支持可视化组合的 Python 工作流，并连接 Jenkins Agent、TAF、测试线配置、KPI 工具和 AI Worker。我负责架构、关键模型和跨模块契约协调。主要风险不是单项功能，而是持续演化：旧用例不能一次重写，测试设备是共享资源，执行时间远超普通 HTTP 请求，不同执行器结果不一，生产凭据又不能进入浏览器和仓库。没有稳定架构，各模块就会围绕临时字段相互依赖。

### 二、基于架构的软件开发方法

基于架构的软件开发以架构为设计和演化主线，包括架构需求、设计、文档化、评估、构件实现、集成验证和演化。架构不是静态框图，而是对结构、关键决策和质量属性的共同约束。

我采用多视图建模：上下文视图说明用户、Portal、API、Jenkins、Agent 和外部工具；模块视图说明路由、服务、仓储和执行处理器；运行时视图描述创建、触发、执行、回调和查询；部署视图描述 Nginx、Controller、Agent 和服务进程；数据视图说明运行、产物、KPI 和 AI 信息。动态流程再用“工作流—阶段—任务项”模型表达串并行与资源范围。

评估时，我把质量目标写成场景：Jenkins 不可用时仍保留运行记录并可重试；新增执行器时前端查询模型不整体重写；两个任务项命中同一 UE 时阻止危险并发；外部 AI 不可用时规则分类仍工作。这些场景用于识别风险、敏感点和权衡点。

在评审中，我按“业务驱动因素—质量属性场景—架构策略—风险”检查方案。运行编号与 Jenkins 构建号分离是可修改性的敏感点；并行执行与资源锁是性能和正确性的权衡点；SQLite 简化部署，却带来容量与单点风险；保留 Jenkins 可复用既有能力，却增加一次跨系统回调。对这些风险不追求一次消除，而是明确当前接受条件、验证办法和后续演化触发条件。

### 三、项目中的具体实践

第一，先建立架构基线。系统冻结 Portal、Platform API、Jenkins Integration 和 Test Workflow Runner 四个模块。API 内部按模式、服务、仓储分层；Jenkins 只管理阶段，复杂 JSON 解析、校验和回调下沉 Python，形成“薄流水线、厚 Python”；Runner 分离请求加载、编排、处理器和结果构建。模块文档记录边界、步骤和验证状态，防止架构只存在于个人记忆。

第二，采用契约优先。平台先冻结运行创建、触发、回调、产物和 KPI 查询契约。运行编号是平台主键，Jenkins 构建引用只是外部标识；执行器类型决定 Robot 或 Python 工作流的校验；工作流结构不包含 Jenkins 细节；产物清单统一索引文件。这样 Portal、Jenkins 和 Runner 可围绕稳定模式分别实现。

第三，通过评估做取舍。FastAPI 直接运行长任务虽然组件少，却把 Web 生命周期与任务耦合；引入新工作流平台能力强，但学习和运维成本高；Jenkins 调度加 Python Runner 可复用现有 Agent、凭据、超时和归档。结合当前规模，我选择第三种。数据层先用 SQLite 存元数据，大文件保留在产物目录，这是部署简单性与容量之间的权衡。

第四，以兼容方式演化。系统从 Robot 路径扩展出 Python 编排器，未改变平台主键和查询主线；KPI 工具逐步收编为内部服务，减少任意命令；随后增加独立工具运行和 AI Worker。AI 第一期只读取证据、生成摘要和根因建议，不直接改环境或重跑 Jenkins。

第五，把验证纳入迭代。模式、服务、仓储和接口使用 pytest 与 TestClient；Jenkins helper 和 Runner CLI 有独立测试；跨接口准备 Postman 和 SQLite 校验；真实 Jenkins、Robot、TAF 由目标环境验证。每个步骤记录问题、文件、调用流、关键字段、命令和预期结果，明确区分“代码实现”与“环境验证”。

### 四、实施效果与改进方向

平台现已形成三类具有代码骨架的执行路径，运行、回调和详情模型保持稳定；阶段、资源锁、时间线、产物和 AI 证据可沿既有架构扩展。当前完成目标环境验证的是接口契约和 Agent 基线，其余路径仍需端到端验证。不足是评估尚未形成完整 ATAM 材料，Portal 测试和生产安全配置仍待补齐。后续将建立架构决策记录，以接口兼容性、任务成功率、恢复时间和变更影响范围评估演化。实践表明，基于架构开发能保护遗留资产，并让多种执行技术围绕共同模型渐进演化。

## 考场改写提示

- 如果题目要求 ABSD 过程，明确写出架构需求、设计、文档化、评估、实现、集成、测试和演化。
- 如果题目要求 ATAM，补充业务驱动因素、效用树、质量属性场景、架构方法分析、敏感点、权衡点和风险；不要声称项目已举行正式 ATAM 会议。
- 如果题目要求系统建模，重点展开上下文、模块、运行时、部署和数据视图，以及 `workflow -> stages -> items` 领域模型。
- 如果题目要求构件化开发，可把 Platform API 分层、Jenkins Python helper、Runner handler 和 internal tools 作为可复用构件说明。
- 如果题目要求模型驱动架构，需增加 CIM、PIM、PSM 和模型转换理论，本项目实践可作为“结构化 workflow 模型生成执行请求”的案例，但不能夸大成完整 MDA 工具链。
