# 第五篇：论持续集成、自动化测试与自动化运维在 5G 测试平台中的应用

## 适配考点

本文主要适配 DevOps、持续集成与持续交付、软件测试方法、自动化运维、配置即代码、可观测性和软件维护类题目。

## 论文正文

### 摘要

我参与了某 5G GNB 自动化测试平台的架构和工程化建设，具体时间、职位和职责须按真实经历确认。项目包含 React、FastAPI、Jenkins、Robot Framework、Python Runner、KPI 工具和 AI Worker，运行在 Windows 开发环境、Debian 服务端和专用 Agent 中。早期部署依赖人工操作与零散文档，容易出现配置漂移、过量重启、证据分散和验证状态误判。为此，我以 Git 作为代码与配置真源，使用 JCasC、Job DSL 和 Pipeline 管理 Jenkins，以 Python 固化复杂构建逻辑，以分层测试和产物形成证据，并按改动路径建立最小发布、验证和回滚流程。本文论述相关方法、实施与改进方向。

### 一、项目背景与工程化问题

平台包含两类活动：测试执行由 Jenkins 在 Agent 上运行 Robot 或 Python 工作流并归档结果；平台发布则更新 FastAPI、AI Worker、Portal、Nginx 或 Jenkins 配置。二者混在一条流水线会使失败边界不清。项目还连接私有仓库、Python、Node.js、系统服务和真实测试线，依赖个人经验难以重复。我负责持续集成、质量分层和部署流程设计，目标是让源码、配置和流水线可版本化、可恢复；每次只执行必要发布动作；测试除结果外还保存输入、环境、命令、日志和回调证据。

### 二、DevOps、自动化测试与自动化运维方法

DevOps 通过开发、测试和运维协作提高交付速度与稳定性。持续集成要求频繁合并并自动构建、测试；持续交付要求软件保持可发布；自动化运维则把配置、部署、监控、故障处理和回滚标准化、代码化。

自动化测试应分层：靠近代码的测试运行快、定位准；接口、数据库、流水线和端到端测试逐层验证集成风险。测试还应具备环境、数据、断言和报告。本项目无法在本地完整模拟 Jenkins 凭据、TAF 和真实设备，因此必须区分代码测试、服务器 smoke 与真实测试线证据。

### 三、项目中的具体实施

第一，建设 Jenkins 配置即代码基线。集成模块按 JCasC、Job DSL、Pipeline 和 Python 脚本分层：JCasC 管 Controller、Agent、环境和 Seed Job；Job DSL 生成 Robot 与 KPI Job；流水线描述检出、环境、执行、归档和回调；Python 负责请求物化、检出计划、命令构建和回调。关键配置可以从 Git 恢复，Job 也能重复生成。

第二，区分测试执行和平台发布。测试流程面向业务运行，输入运行编号、测试线、用例或工作流，输出状态、时间线、产物和 KPI；平台发布面向代码版本，更新 API、Portal、Worker 或 Nginx。测试已有 Jenkins Pipeline，平台发布当前主要依靠检查清单和人工服务器操作，尚无仓库内可核验的独立发布流水线。前端由具备 Node.js 的构建机生成静态产物，服务器只负责提供文件。

这种分离使一次测试失败不会被误判为平台发布失败，也避免 Portal 更新时运行真实设备回归；两类流程可以分别设置触发权限、输入参数、验证步骤和回滚范围。

第三，采用“薄流水线、厚 Python”。Groovy 擅长阶段、Agent、凭据和归档，复杂参数处理却难单测。因此流水线只保留阶段，Python 先生成请求、检出、环境、命令和回调计划，再执行。脚本可用 pytest 覆盖正常与异常分支，物化结果又能作为失败复盘证据。

第四，建立分层质量体系。平台接口使用模式、服务、仓储测试和隔离 SQLite；Runner 验证请求加载、阶段任务、并行安全、结果和命令行；Jenkins helper 有独立测试；Postman、SQL 和 JMeter smoke 分别验证跨接口、数据和最小性能；pytest 生成 Allure 原始结果，Robot XML、日志和报告作为执行证据。真实 Jenkins、Robot、TAF 与设备仍由目标环境验证并回填记录。

第五，建设运行证据。每次运行围绕平台编号规划保存请求、检出计划、环境计划、命令、控制台、Runner 结果、Robot XML、回调和 KPI 元数据。多数证据已有归档入口，但回调结果仍需调整归档顺序才能保证失败时长期保存。Portal 聚合阶段、进度、产物和 AI 结果，AI Worker只根据可取得证据生成失败层和建议，并保留依据与置信度。

第六，按变更路径最小发布。API 改动只重启 API，Worker 改动只重启 Worker，Portal 改动重新构建，Pipeline 改动通常不重启 Jenkins，Job DSL 改动运行 Seed Job，JCasC 改动才重启 Jenkins，Nginx 变更先检查再加载。服务器只拉取受控 Git 版本；故障时以提交号为锚点回退，再执行对应组件的最小生效动作。

### 四、实施效果、不足和持续改进

项目目前具备 Jenkins as Code 骨架、Robot/KPI Pipeline、Python helper、分层测试、产物回调和发布检查流程；Agent smoke 与平台核心契约已有验证记录。项目能区分“代码实现”“自动化测试”“服务器 smoke”和“真实端到端”，减少状态误判。当前 Portal 测试框架、真实 KPI/TAF 回归及部分服务配置仍待补齐，也没有容器编排和弹性伸缩。后续将补充前端测试、质量门禁、制品版本、自动 smoke，并以任务成功率、构建时长、变更失败率和恢复时间度量。自动化运维不是把人工命令写成脚本，而是把配置、测试、证据、发布和恢复组织为可重复、可追踪的工程流程。

## 考场改写提示

- 如果题目要求资源编排、弹性伸缩等云上自动化运维实践，应改用本人确有云环境落地经历的项目；本项目只能支撑 Debian/Jenkins 平台运维。
- 如果题目是“软件测试方法”，增加黑盒、白盒、单元、集成、系统、验收和回归测试理论，重点展开分层测试与目标环境验证。
- 如果题目是“持续集成与交付”，重点写 Git、质量门禁、制品、环境晋级、部署、回滚和度量。
- 如果题目是“软件维护”，从纠错性、适应性、完善性和预防性维护分类，再映射发布检查、配置入库、测试回归和架构演化。
- 不要把当前系统写成已经使用 Kubernetes、服务网格或云原生数据库；如题目强制要求，应改用本人确有实践的项目。
