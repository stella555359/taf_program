# 第一篇：论分层架构与面向服务架构在 5G 自动化测试平台中的应用

## 适配考点

本文主要适配软件架构风格、层次式架构、面向服务架构、企业应用集成、接口契约和异构系统集成类题目。

## 论文正文

### 摘要

我参与了某 5G GNB 自动化测试平台的架构设计与核心建设，具体时间、职位和职责须按本人真实经历确认。项目要把 React 门户、FastAPI、Jenkins、Robot Framework、Python 工作流、KPI 生成与异常检测整合为统一平台。原有方式依赖工程师直接操作 Jenkins，存在入口技术化、凭据边界不清、状态和报告分散等问题。为此，我采用分层架构与面向服务思想，划分门户、平台接口、调度、执行、后处理和数据展示层，以运行、回调和产物契约连接各层，并用平台运行编号隔离 Jenkins 构建编号。该设计已形成提交、调度、回写和展示的代码主链路，其中接口契约与 Agent 基线已有验证记录，真实 TAF、KPI 和完整端到端链路仍待验证。本文重点论述架构选型、关键设计及效果。

### 一、项目背景与架构挑战

平台既要运行传统 Robot 用例，也要执行由阶段和任务项组成的 Python KPI 工作流，结束后还可能生成 Excel 和异常报告；同时必须复用 Jenkins、Linux Agent、robotws、测试线配置、TAF 和 Compass。作为架构与接口设计参与者，我识别出四项矛盾：普通用户难以正确填写 Jenkins 技术参数；浏览器直连 Jenkins 会暴露凭据并混淆业务状态与构建状态；不同执行器输入输出不一，长任务不适合占用 Web 请求；XML、HTML、Excel 和日志等大文件不宜全部存入数据库。因此系统不能继续把能力堆入流水线脚本，也不宜盲目拆成大量微服务，我选择“分层定职责、服务契约做连接、模块化渐进演化”的方案。

### 二、分层架构和面向服务架构的理解

分层架构按职责组织系统，上层通过明确接口使用下层能力，优点是关注点分离、依赖清晰、便于替换和测试，缺点是层次过多会增加调用开销。面向服务架构把业务能力封装为具有明确契约的服务，强调自治、松耦合和可组合，必须同时定义请求响应、状态、错误和安全边界。本项目用分层确定“谁负责什么”，用服务契约确定“异构组件如何协作”：进程内采用模式、服务、仓储分层，进程间采用 REST、JSON、回调和产物清单。

### 三、项目中的架构设计与实施

首先，我划分六个逻辑层。React 门户负责表单、工作流编排和展示，不保存 Jenkins 凭据；FastAPI 平台层负责创建运行、校验契约、持久化、触发和聚合；Jenkins 调度层负责 Agent、超时、凭据和归档；执行层保留 Robot，并新增 Python Runner 处理阶段内串并行；后处理层封装 KPI 生成和检测；数据层以 SQLite 保存结构化元数据，以 Jenkins 产物或文件系统保存大文件。Nginx 将外部访问收口为门户、接口和 Jenkins 三类路径。

其次，我以契约降低耦合。平台先生成稳定的运行编号，再由独立接口触发 Jenkins，使业务主键不依赖队列号或构建号，触发失败也能保留记录。执行器类型区分 Robot、Python 编排器和独立工具：前者要求用例路径，后者要求工作流结构。执行结束后，Jenkins 或 Worker 回写状态、构建引用、时间、KPI 摘要和产物清单；前端只查询平台接口，不解析 Jenkins 工作目录。

为保证服务契约可治理，我在模式层规定必填字段、状态语义和错误边界，在服务层校验执行器与参数组合，在仓储层统一保存运行状态。创建与触发分成两个接口：创建成功后即返回运行编号，触发失败则记录失败状态并允许重试。回调只传结构化摘要和产物索引，不把执行器内部对象直接暴露给前端。这样既便于接口自动化测试，也为以后增加新执行器或替换调度器留下兼容空间。

再次，我实行“元数据入库、大文件外置”。SQLite 保存状态、时间、工作流、构建引用、产物清单及 KPI 摘要；Robot 的 XML、HTML，Runner 结果和 KPI 报告保存在产物目录。产物清单作为统一索引，使 Portal 和 AI Worker 无须了解各执行器的物理路径，也避免数据库膨胀。

在依赖方向上，我禁止门户跨过平台接口直接访问执行层，也不让 Runner 反向依赖前端模型。Jenkins 仅承担调度、凭据、超时和归档，业务工作流语义留在 Python Runner 中。该约束避免了“为了少一次调用而跨层访问”的捷径，使每一层可以用自己的测试方式验证。

最后，我比较了三个方案。Portal 直连 Jenkins 实现快，却会泄露凭据和技术细节；FastAPI 直接启动所有进程虽然组件少，但长任务的超时、取消和日志归档复杂；全部改成 Robot 难表达动态工作流，全部改成 Python 又浪费成熟用例。因此我保留 Jenkins 调度，采用双执行器共存，并以统一运行契约屏蔽差异。

### 四、实施效果、不足与改进

系统目前形成四个主模块和三类已建模执行路径。平台运行、回调、产物和 KPI 查询契约及 Agent 最小执行已有验证记录；Portal 代码可按同一运行编号聚合状态、产物和 AI 信息，真实测试线与完整后处理仍待端到端验证。新增执行器时，主要扩展请求模式、处理器和 Jenkins Job，门户的运行模型与查询接口可以保持稳定，体现了高内聚、低耦合的设计目标。当前 SQLite、单 Jenkins 和单实例服务适合轻量阶段，不能宣称多活；认证、回调鉴权和容灾也需加强。后续将在保持契约兼容的前提下补充身份认证、幂等回调、监控和数据库迁移机制。实践说明，架构价值不在组件数量，而在于以分层和稳定契约控制复杂度，并保护既有 Jenkins 与 Robot 投资。

## 考场改写提示

- 如果题目要求“列举架构风格”，理论段先写数据流、调用返回、分层、事件驱动等风格，再重点说明为何选择分层与面向服务。
- 如果题目要求“SOA 的关键技术”，补充服务契约、服务注册或配置、消息通信、服务组合和治理；不要虚构本项目已经使用 ESB。
- 如果题目要求“微服务”，应明确当前项目是独立模块和服务化边界，不是完整微服务集群；可以写演进条件和拆分策略。
- 如果题目要求“企业集成”，重点保留 Jenkins、Robot、TAF、KPI 工具和 Portal 的异构契约设计。
- 把“我承担总体架构设计”修改为本人真实职责，并补充真实团队规模和效果数据。
