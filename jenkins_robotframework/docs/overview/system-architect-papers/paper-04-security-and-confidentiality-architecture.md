# 第四篇：论安全架构与保密性设计在 5G 自动化测试平台中的应用

## 适配考点

本文主要适配信息系统安全架构、安全性与保密性设计、身份鉴别、访问控制、数据安全、DevSecOps 和 AI 安全类题目。当前项目只能用于说明零信任的信任域划分和演进设计，不能作为零信任已落地案例。

## 论文正文

### 摘要

我参与了某 5G GNB 自动化测试平台的架构与核心建设，具体时间、职位和职责须按真实经历确认。平台连接 Web 用户、FastAPI、Jenkins、Linux Agent、Robot、Python Runner、KPI 工具和外部 AI，包含令牌、SSH 私钥和业务账号，也会产生设备信息、日志和报告。Portal 直连 Jenkins、流水线接受任意命令或敏感日志直接送入外部模型，都可能造成凭据泄露、命令执行和数据外传。为此，我依据纵深防御与最小权限原则，从信任边界、身份凭据、输入执行、传输存储、证据追踪和 AI 边界实施防护，并把非严格主机校验、回调 TLS 和鉴权缺口列入加固计划。

### 一、项目背景与威胁分析

用户经 Portal 提交 Robot 用例或 Python 工作流，平台保存运行并触发 Jenkins，Agent 再访问仓库、测试配置和设备，最后归档报告；AI Worker还会读取证据生成根因建议。我负责安全边界和接口防护要求，识别出六类威胁：浏览器获得 Jenkins 凭据后越权；私钥和密码进入源码或日志；用户输入被拼接为任意命令；伪造回调篡改状态；产物或 AI 输入泄露内网与账号；Agent、Jenkins 或外部模型失陷后扩大影响。因此设计必须同时保障机密性、完整性和可用性。

### 二、安全架构设计方法

安全架构围绕机密性、完整性、可用性、鉴别、授权和审计建立控制。我遵循最小权限、纵深防御、默认拒绝、职责分离和安全失败原则，并以“主体—客体—操作—条件”分析访问控制。

实施时先绘制数据流和信任边界，区分浏览器、平台服务、Jenkins 控制、Agent、设备和外部 AI 区；再对身份、凭据、代码、参数、产物和日志分级，在网络、应用、数据和运维层设置控制；最后以日志、运行状态和构建记录形成技术证据链。当前尚无可信操作主体，不能把证据链写成完整审计体系，也不能用 HTTPS 代替认证和回调签名。

针对每条跨边界数据流，我从身份伪造、数据篡改、信息泄露、权限提升和拒绝服务五方面检查威胁，并按发生可能性与影响确定优先级。凭据泄露和任意命令属于高风险，应在入口和执行端共同控制；报告中的内网信息属于保密风险，应在存储、下载和 AI 输入三个位置处理；服务暂时不可用则通过状态保留和重试降低影响。该方法使安全措施与具体资产、入口和责任模块对应，而不是简单罗列加密算法。

### 三、项目中的安全设计与实践

第一，隔离 Portal 与 Jenkins。普通用户的测试提交固定经过“Portal—平台接口—Jenkins”，浏览器不保存 Jenkins 令牌。平台负责参数校验和 Job 映射；Jenkins 管理界面只供获授权运维人员使用。Nginx 以 HTTPS 统一入口并分开代理门户、接口和 Jenkins 路径。

第二，外置凭据并分离职责。架构要求 Agent 启动密钥、仓库密钥、Jenkins 凭据、Compass 账号和回调令牌使用不同引用，避免一把密钥贯通所有系统。真实秘密不得进入 Git，只能由 Jenkins Credentials、环境变量或服务器受控文件注入。仓库已有部分配置入口，但真实服务器是否完成全部分离仍需部署证据确认。Controller 不执行业务任务，Job 按标签调度到指定 Agent。

第三，限制输入和执行能力。平台使用 Pydantic 模式和服务校验执行器契约；Runner 把操作建模为目录、阶段、任务项和处理器，并校验资源与并行规则；KPI 工具逐步由任意命令改为内部服务参数调用。流水线先把请求物化为 JSON 和执行计划，再生成命令，便于测试与复核。当前措施降低了任意输入风险，但 Robot 路径边界、附加参数以及部分流量处理器的命令入口仍需收紧。

第四，保护传输、存储和输出。外部入口使用 TLS；SQLite 只保存状态、摘要、路径和链接，大文件保存在 Jenkins 产物或受控目录，便于分别设置权限、保留期和备份。日志不得包含密码、令牌和私钥；证据发送外部 AI 前应脱敏账号、内网地址和设备标识，并限制长度与类型。

对于 AI 输入，还需把日志内容视为不可信数据，防止其中的自然语言被误当成控制指令。分析服务只能读取允许的证据类型，输出仅作为建议并标注置信度，涉及重跑、环境修改或发布决定时必须由人工确认。

第五，建立完整性与追踪链。平台运行编号贯穿创建、触发、构建、回调、产物、KPI 和 AI 分析；构建引用、任务时间线和产物清单保留执行事实；AI 结果保留证据、置信度和人工确认标志。它能回答某次运行对应的构建、阶段和依据，但因缺少用户认证与可信操作者字段，还不能回答“谁触发了什么”。AI 只做摘要、根因和报告，不自动重跑、改环境或决定发布。

第六，把安全约束纳入交付。JCasC、Job DSL、Pipeline 和部署文件纳入版本管理；发布按变更路径选择服务重启、前端构建、Seed Job 或 Nginx 操作；Nginx 变更先检查配置，代码测试覆盖模式、接口、Runner 和 Jenkins helper，降低安全规则在演化中被绕过的风险。

### 四、效果、遗留风险与加固计划

当前代码已实现浏览器不直接持有 Jenkins 凭据、结构化运行契约和 AI 人工确认边界，但不能描述为完整生产安全体系。联调环境仍可能使用非严格主机校验、不安全回调 TLS 或关闭脚本沙箱；完整认证、RBAC、回调签名、重放防护、可信操作者和自动脱敏仍待加固。后续将接入统一身份认证，按角色授权；为回调增加短期令牌、时间戳、签名和幂等键；启用严格证书与主机指纹校验；建立日志脱敏、凭据轮换和恢复演练。安全架构不是最后增加一个登录页，而是从信任边界、执行能力、数据生命周期和运维过程共同约束风险。

## 考场改写提示

- 如果题目要求安全体系结构，可按物理、网络、系统、应用、数据、管理六个层次重新组织实践段。
- 如果题目要求零信任，当前项目只能说明“持续验证、显式授权、最小权限、假设已失陷”等原则下的信任域划分和演进设计；若题目要求已落地实践，应改用本人另有真实实施经历的项目。
- 如果题目要求保密性，重点扩展数据分类分级、加密、脱敏、密钥生命周期、访问审计和销毁。
- 如果题目要求 DevSecOps，重点保留配置即代码、schema 测试、凭据扫描、发布检查和生产加固。
- 论文中的 RBAC、callback 签名等属于改进计划；只有在本人真实项目已落地后，才能改写为完成效果。
